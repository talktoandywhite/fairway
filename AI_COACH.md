# AI Coach & Caddy — Design Specification

How Fairway uses an LLM to give every athlete a coaching voice, and the constraints that keep it
trustworthy when the person on the other end is twelve.

Read alongside [`CLAUDE.md`](./CLAUDE.md). Where the two conflict, `CLAUDE.md` wins.

---

## The one-sentence version

**A deterministic engine decides what the athlete should do; the LLM decides how to say it.**

That separation is the whole design. Everything below is an elaboration of it, and most of the failure
modes in this feature come from blurring it.

---

## Why the separation matters

The tempting build is: give the model the athlete's data and ask it to produce a training plan, a
tournament strategy, and some encouragement. It demos beautifully. It is also the version where a
language model prescribes squat loads to a fourteen-year-old, invents a tournament that does not
exist, and tells a kid who just shot 121 something that reads as kind and lands as devastating.

So the architecture is:

```
┌──────────────────────────────────────────────────────────────┐
│  DETERMINISTIC LAYER  — decides substance                     │
│                                                               │
│  • Stats engine (lib/stats)     what the numbers say          │
│  • Plan engine                  which phase, which block,     │
│                                 which template, which drill   │
│  • Rules                        gap warnings, ratio checks,   │
│                                 progression eligibility       │
│  • Vetted content library       exercises, drills, coaching   │
│                                 cues — human-authored         │
└───────────────────────────┬──────────────────────────────────┘
                            │  structured facts + selected content
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  LLM LAYER  — decides voice                                   │
│                                                               │
│  • Selects among pre-approved content where choice exists     │
│  • Phrases it for this athlete's age and this coach's style   │
│  • Never originates a prescription, a number, or a fact       │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  SAFETY LAYER  — decides whether it ships                     │
│  moderation → grounding check → age-band check → log → render │
└──────────────────────────────────────────────────────────────┘
```

If the model is ever the only thing standing between an athlete and a bad instruction, the design is
wrong.

---

## What ships when

**V1.5 — ambient only.** No chat box. The LLM writes into surfaces the athlete already visits.
Every generation is server-side, triggered by an app event, reviewable, and logged.

**V2 — bounded conversational caddy.** Only after the ambient layer has proven the voice system and
the moderation, escalation, and eval infrastructure exists.

The reason for this order is not caution for its own sake. An ambient message is generated from a
known context at a known moment, so you can evaluate it offline against a fixed test set. A chat turn
is generated from arbitrary user input, so you cannot. Build the thing you can measure first.

---

## The five ambient surfaces

| Surface | Trigger | What it says | Length |
|---|---|---|---|
| **Post-round debrief** | Round logged | What the numbers actually say about that round, one thing that went right, one leak to attack next | 3–4 sentences |
| **Tournament plan note** | Event added or approaching | What this event is for in the arc of the season, what "a good day" looks like here | 2–3 sentences |
| **Weekly training focus** | Start of week | The week's priority in plain language, tied to the current phase and the athlete's worst leak | 2–3 sentences |
| **Workout block intro** | Block transition | Why this block exists, what it's building toward, what to watch for | 3–4 sentences |
| **Dashboard line** | Dashboard load, cached daily | One line of orientation — progress, streak of the *right* kind, or a nudge | 1 sentence |

Note what is absent: no push notification generated by an LLM, no unprompted message, no daily
check-in. Ambient means *present when the athlete arrives*, not *arriving unbidden*.

Every surface renders with an AI label and a feedback control. See Attribution and Feedback below.

## The athlete context object

Exactly one function assembles what the model sees: `buildAthleteContext(athleteId, surface)`. Nothing
else may construct a prompt. It returns a typed, minimized, auditable object.

```ts
type AthleteContext = {
  // Developmental — drives vocabulary, sentence length, and safety limits
  ageBand: 'u12' | '12-14' | '15-17' | '18-22'

  // Competitive framing
  level: 'junior' | 'high_school' | 'college'
  gender: 'male' | 'female' | 'unspecified'   // structured use only — see below

  // Goal — the athlete's own words carry the school/program context
  goal: { metric: string; target: number; deadline: string; why: string }

  // Performance — from the deterministic stats engine, never recomputed by the model
  scoringAverage: number | null
  lastThreeAverage: number | null
  strokesToGoal: number | null
  trend: 'improving' | 'flat' | 'declining' | 'insufficient_data'
  leaks: Array<{ name: string; currentPerRound: number; target: number; strokesSaved: number }>
  worstLeak: string | null

  // Plan state
  currentPhase: { name: string; mainJob: string; scoreTarget: string; daysRemaining: number }
  currentBlock: { name: string; focus: string } | null
  nextEvent: { name: string; daysAway: number; priority: string } | null
  longestGapDays: number | null

  // Practice
  minutesByType: Record<SessionType, number>
  practiceRatioVerdict: 'balanced' | 'too_much_full_swing' | 'too_little_short_game' | 'insufficient_data'

  // Surface-specific payload (the round just logged, the event, the block)
  subject: unknown

  // Voice
  voice: VoiceProfile
}
```

**What is deliberately not in it:** athlete name, coach name, school name, city, date of birth,
email, parent identity, any free text written by another user, any raw table rows. The model gets
computed facts and vetted content. It does not get the database.

### On gender

Used for **eligibility and physiological programming only** — division and tour eligibility, tee
selection, and which strength-progression norms the deterministic plan engine applies. It is passed
to the model solely so that generated text does not contradict those facts.

It **must not** influence tone, encouragement style, assumed competitiveness, or assumed
emotional register. This is stated in the system prompt as a hard constraint and is covered by a
standing eval: the same context with gender flipped must produce materially equivalent output on
every tone dimension. If it does not, the prompt has a bug.

`unspecified` is always a valid value and never blocks a feature.

### On age

`ageBand`, not date of birth — the model has no use for the precise date and every reason not to have
it. The band drives three things: vocabulary and sentence length, how much technical detail is
included, and the **hard content limits** in the next section.

---

## Hard content rules

These are enforced at three layers — system prompt, output classifier, and rendering. Belt, braces,
and a third thing.

**Never, at any age:**

- Weight, body composition, dieting, calories, nutrition, or supplements. Not even encouragingly, not
  even when asked. This is the single highest-risk category for this user population and the rule is
  absolute.
- Medical advice, injury diagnosis, pain management, or return-to-play judgment. Pain routes to
  "stop and talk to an adult and a medical professional," always.
- Mental health intervention. Distress signals route to the escalation path, not to counsel.
- Specific loads, weights, or progressions not present in the vetted exercise library.
- Comparison to a named other athlete.
- Any statement about making or not making a team, a roster, a college, or a scholarship. The app
  tracks a gap to a number; it does not forecast outcomes.
- Certainty about the future. "If the three-putts keep dropping, the average follows" — not "you'll
  be at 100 by March."

**Age-band adjustments:**

| Band | Register | Detail | Notes |
|---|---|---|---|
| `u12` | Short sentences, concrete, playful. No jargon. | One idea per message | Effort and fun over outcome, always |
| `12-14` | Plain, direct, a little dry humor lands | One or two ideas, light jargon with a gloss | The reference athlete's band |
| `15-17` | Peer-adjacent, no talking down, honest about hard numbers | Full stat vocabulary | Recruiting pressure is real here — do not add to it |
| `18-22` | Adult, analytical, terse | Strokes-gained vocabulary, assumes fluency | Least hand-holding |

**Tone floor, independent of coach settings:** never contemptuous, never sarcastic at the athlete's
expense, never shaming a missed session or a bad round, never implying the athlete is behind or
disappointing anyone. A coach can dial directness up. A coach cannot dial kindness to zero.

## The voice system

A coach's style is expressed through **bounded parameters**, not free text.

```ts
type VoiceProfile = {
  preset: 'encouraging' | 'direct' | 'analytical' | 'old_school'
  warmth: 1 | 2 | 3 | 4 | 5        // floor of 2 enforced regardless of setting
  directness: 1 | 2 | 3 | 4 | 5
  technicality: 1 | 2 | 3 | 4 | 5   // capped by ageBand
  humor: 1 | 2 | 3 | 4 | 5
  signaturePhrases: string[]        // max 3, from a vetted list, coach-selected
}
```

Each parameter value maps to a **curated prompt fragment written and reviewed by the Fairway team**.
The coach composes from a palette; the coach does not write the prompt. This is not a limitation to
apologize for — it is the reason the system can be evaluated at all. Twenty combinations you can test
beat infinite combinations you cannot.

`technicality` is capped by age band: a coach who sets 5 gets 5 for their college players and 3 for
their twelve-year-olds, automatically and without being asked.

**Where the voice applies:** a coach's voice profile applies to athletes linked to that coach. An
athlete with no coach gets the `encouraging` default. An athlete with two coaches uses the profile of
whoever is marked primary.

**Preview before save.** The coach settings screen renders live samples of all five surfaces against
a fixture athlete, so a coach sees exactly what their athletes will see before committing. No coach
should ever be surprised by what went out under their program's banner.

**V2 — style distillation.** A coach writes freely about how they coach; an offline job proposes a
`VoiceProfile` plus a short voice summary; the coach reviews and approves it. The output is still
bounded parameters. The free text never reaches a live prompt.

## Attribution — the impersonation problem

If a message written by a model appears in a coach's voice, the coach is being impersonated to a
minor, and the athlete may act on it believing their coach said it. That is a trust failure and
plausibly a liability one.

The rules:

1. **Every generated message is visibly labeled as AI.** A subtle icon is not enough — the label is
   text, in the component, always.
2. **Attribution is to the style, not the person.** "Styled to Coach Clark's approach," never
   "Coach Clark says."
3. **A coach opts in** to having their voice profile used for ambient messaging, and can revoke it,
   which takes effect on the next generation.
4. **Anything carrying a coach's name in a substantive way** — an assigned drill, a lesson note — is
   coach-authored or coach-approved, never model-originated.
5. **Athletes and parents can turn the AI layer off entirely** without losing any other functionality.
   Every surface degrades to its deterministic content. This must be tested.

## Safety pipeline

Every generation passes through all six stages. No bypass, no exceptions, no "internal" path.

```
1. CONTEXT      buildAthleteContext() — minimized, typed, no PII
2. COMPOSE      system prompt + age fragment + voice fragments + surface template
3. GENERATE     provider call, low temperature, hard token cap, timeout
4. MODERATE     output classifier: banned categories, tone floor, PII leakage
5. GROUND       every number in the output must appear in the context object
6. LOG          full record: context hash, prompt version, output, verdicts, latency
```

**Stage 5 is the anti-hallucination control and it is mechanical, not judgmental.** Extract every
numeral from the generated text; each must match a value in the context. A debrief that says "your
three-putts are down to 3.1" when the context says 4.2 fails the check and is discarded. This catches
the failure mode that matters most in a data product: confident, specific, wrong.

**On failure at any stage**, the surface renders its deterministic fallback — a plain, useful,
template-generated string. **Every AI surface has a fallback and the app is fully usable without the
AI layer.** Build the fallback first, then wrap it.

**Kill switch:** a single flag disables all generation globally, and a per-surface flag disables one.
Both are runtime, not deploy-time. Verify these work before the first athlete sees a generated word.

## Escalation

The ambient layer does not accept athlete input, so the escalation surface in V1.5 is small but not
zero — free-text fields the athlete types (round notes, practice results, lesson homework notes) pass
through the app.

If a distress signal appears in athlete-authored free text, the system does not generate a response to
it. It surfaces a quiet, non-alarming resource card to the athlete, and — for athletes under 18 with a
linked guardian — flags for guardian visibility. **The model is never the responder.** It is not a
counselor, it is a caddy, and the gap between those is where people get hurt.

This gets specified properly with qualified input before V2's chat feature. Do not improvise it.

## Evaluation

The eval suite is the deliverable that makes this feature maintainable. Without it, every prompt
change is a coin flip.

**Fixture set:** 40+ athlete contexts spanning all four age bands, all four presets, both genders and
unspecified, and the cases that break things — zero rounds logged, a 30-stroke outlier, a declining
trend, a met goal, a 90-day gap, all leaks at target, insufficient data everywhere.

**Assertions per generation:**

- Banned category classifier returns clean
- Every numeral is grounded in the context
- Reading level within the age band
- Length within the surface's bounds
- Tone floor satisfied
- No name, school, or location present
- Gender-flip pair produces materially equivalent tone

**Adversarial set:** athlete-authored free text engineered to inject instructions, extract the system
prompt, or elicit a banned category. Every one must fail to influence the output. Prompt injection
through user-generated content is the realistic attack here, not a jailbreak typed into a chat box —
because in V1.5 there is no chat box, but there is a round-notes field.

**Run the suite in CI on every prompt change.** Prompts are versioned artifacts in `lib/ai/prompts/`,
reviewed like code, never edited in a dashboard.

## Cost and performance

Ambient generation is event-driven and cacheable, which makes it cheap if you are disciplined.

- Post-round debrief: once per round, cached on the round record permanently
- Tournament note: once per event, regenerated only if the event materially changes
- Weekly focus: once per athlete per week
- Block intro: once per block transition
- Dashboard line: once per athlete per day

That is roughly 6–10 generations per athlete per week at steady state. Cache on a hash of the context
object so an unchanged context never regenerates. Generate asynchronously after the triggering write
and render the fallback until it lands — never block a user action on a model call.

Budget alerting per athlete, per coach, and globally. A runaway regeneration loop should page someone
before it invoices someone.
